# HELP-01 — точный результат подготовки объяснения

**ТЗ разработчику · 24 ноября 2026 · статус: предложено к реализации.**

Добавить в собственную Help явный результат подготовки Explain и показывать подходящее сообщение в существующем окне помощи. Сейчас разные причины отсутствия плана превращаются в один `null`: противоречивая расстановка, незавершённая проверка и отсутствие хода среди реализованных правил. Игрок во всех случаях видит одинаковое «нет доказуемого хода», хотя это разные ситуации.

**Один механизм, два связанных этапа:** типизированная подготовка → отображение её результата. Новая стратегия решения в этот пакет не входит. В приложенных материалах воспроизведён текущий пробел; реализация и продуктовая приёмка ещё не выполнены.

Основной `sourceFeatureId`: **`guru-solver-single-pass-result`**, текущая запись ledger — **RESEARCHED / PARTIAL**. Берём архитектурный приём из конкретного исходного кода Guru: результат вызова, найденные шаги и завершение поля имеют разный смысл. Наша классификация причин отказа — самостоятельная адаптация этого приёма, а не восстановленный enum оригинала.

### Воспроизводимое различие

В собственной связной задаче с пятью неизвестными есть две строки: `a − b = c` и пересекающая её через `b` вертикаль `b ÷ d = e`. Лоток — **5, 4, 1, 2, 2**. Единственное числовое решение по cell ID: **[5, 4, 1, 2, 2]**.

Публичный `parsePuzzle` принимает геометрию. Текущий `countSolutions` возвращает `{count: 1, exhausted: false}`, а текущий `explain` — `null`. Отдельный Python-перебор физических токенов подтверждает единственность. Следовательно, этот `null` не означает, что у поля нет решения. Это собственная исследовательская fixture, не задача Guru и не добавление в продуктовый банк.

Ту же внешнюю форму `null` дают ещё три разные причины:

| Case | Вход / контроль | Текущий результат | Требуемый результат подготовки |
| --- | --- | --- | --- |
| `incompatible_partial` | В этой задаче игрок ставит `t0 = 5` в общую клетку `b` | `count=0`, `exhausted=false`, `plan=null` | `incompatible_position` |
| `unique_no_supported_step` | Начальная задача с лотком 5,4,1,2,2 | `count=1`, `exhausted=false`, `plan=null` | `no_supported_step` |
| `compatibility_budget_zero` | Та же решаемая задача; тестовый budget=0 | `count=0`, `exhausted=true`, `plan=null` | `budget_exhausted`, phase=`compatibility` |
| `proof_budget_42` | Собственная задача той же геометрии, лоток 3,1,2,1,1; budget=42 | Проверка совместимости закончилась: `count=1`, `exhausted=false`; плана нет | `budget_exhausted`, phase=`proof_search` |
| `proof_budget_normal_control` | Тот же лоток; обычный budget=40000 | Проверяемый `tray`-план: `b=1` | `ready` |

Последняя пара отделяет нехватку бюджета именно во втором этапе от несовместимости и отсутствия поддерживаемого правила: при том же входе обычный лимит даёт план, который принимает существующий независимый verifier. Низкие лимиты — намеренно введённые тестовые условия, а не измерение частоты проблем в выпущенном банке.

## 4. Этап A — transient контракт подготовки

Ввести отдельный тип результата подготовки Explain. Название функции можно согласовать с текущим API, например `prepareExplanation(puzzle, attempt, budget)`. Ниже собственный контракт, не код оригинала и не готовая реализация:

```ts
type ExplainPreparation = {
  snapshot: { attemptId: string; puzzleId: string; boardRevision: number };
} & (
  | { outcome: 'ready'; plan: HintPlan }
  | { outcome: 'incompatible_position' }
  | { outcome: 'no_supported_step' }
  | { outcome: 'budget_exhausted'; phase: 'compatibility' | 'proof_search' }
  | { outcome: 'unavailable'; reason: 'not_playing' }
);
```

Правила переходов:

1. Неподходящий статус попытки даёт `unavailable`. Окно и сейчас не открывается после победы; это внутренний полный контракт, а не новая ошибка для игрока.
2. `countSolutions.exhausted === true` всегда даёт `budget_exhausted / compatibility`, независимо от `count`. `count=0` при исчерпанном лимите **не доказывает** несовместимость.
3. Только завершённая проверка с `count === 0` даёт `incompatible_position`.
4. Завершённая проверка с допустимым продолжением разрешает существующий поиск Direct/tray/intersection. Его прежние приоритеты, порядок и assignments сохраняются.
5. `HintBudgetExceeded` при построении локального evidence даёт `budget_exhausted / proof_search`. Если к этому моменту накоплены неполностью проверенные предложения, не выдавать их как `ready`.
6. Если доступные правила закончили работу без предложения, вернуть `no_supported_step`. Это утверждение о текущем наборе правил; оно не является заключением о невозможности решения или необходимости source-style assumption.
7. `ready` содержит прежний `HintPlan`. Это подготовленное предложение для штатной проверки при Apply, а не факт оплаты, применения или победы.

Сохранить действующие defaults: Explain 40 000 для content-v1 / 160 000 для content-v2; verifier 80 000 / 200 000. В текущем алгоритме compatibility и локальный поиск используют отдельные проходы с этим лимитом; не менять их бюджетную политику в рамках упаковки результата. Неожиданное исключение не превращать в `incompatible_position`.

Результат живёт только между выбором Explain и закрытием/сменой состояния окна. Session передаёт его UI; применение получает **только `ready.plan`** и проходит существующий `verifyExplanation`/revision/materialization/payment. При смене attempt, puzzle или revision подготовка сбрасывается. Можно временно оставить старую `explain(): HintPlan | null` как совместимый wrapper для прежних callers и тестов; новый UI не должен восстанавливать причину из `null`.

`HelpReceipt`, codec и schema сохраняются. Неподготовленный ход не вызывает `session.help`; прежний низкоуровневый `help(..., null) → no_step` остаётся совместимым отказом. Подготовка и её результат не записывают wallet, assisted, hintsUsed, lives, placements, историю или новые аналитические события.

### Почему Endless имеет нейтральную проекцию

`chooseHelp` вычисляет preview **до** Apply. Забег становится assisted только после успешного применения в `GameSession.help`. Если бесплатный preview начнёт точно сообщать несовместимость, игрок получит дополнительную проверку до Submit, сохранив solo-статус. Это меняет смысл принятого режима. Поэтому внутренние причины доступны тесту и caller, но в Endless `incompatible_position` и `no_supported_step` отображаются одинаково: одинаковый текст, кнопки, цвет, accessibility-сообщение и отсутствие correctness cue. Полностью заполненное Endless-поле до Submit остаётся `playing`: правильная раскладка даёт внутренний `no_supported_step`, неправильная — `incompatible_position`, а внешняя проекция у них одна. Подготовка не объявляет ни победу, ни правильность полного поля и не подменяет Submit. Это отдельно воспроизводят два full-board cases. Частоты/тайминги алгоритма этим ТЗ не скрываются; новая явная подсказка о правильности не появляется.

Обычный отказ не выделяет конкретную клетку как виновную: global count=0 не является доказательством индивидуальной ошибки этой клетки. В Daily отказ не отнимает жизнь. «К полю», Back и смена Explain ↔ Reveal продолжают штатный сценарий без списания. При переходе к Reveal старый Explain-статус очищается; для Reveal используется существующий собственный сервис и его прежний отказ, а не новая классификация Explain.

- Ширина Help — `min(viewport − 16px, 510px)`: **304 CSS px** при 320×480 и 320×568; **374 CSS px** при 390×844. Padding 16px; border 1px; внутренние ширины соответственно 270 и 340 CSS px.

- Нижний отступ 8px, в browser добавляется safe-area inset; native root уже владеет inset. `#help-content` прокручивается отдельно; нижний ряд «К полю / Применить» имеет `flex: none`. Минимальная высота кнопок — 48 CSS px.

Это проверенные параметры исходного CSS, **не измерение Android dp и не новый кадр физического телефона**. В приёмке разработчик прикладывает реальные `getBoundingClientRect` и кадры существующего окна на 320×480, 320×568 и 390×844, RU/EN, 100%, затем короткую запись на телефоне. Новые арт, анимации, звуки или вибрации для сообщения не требуются. На простое обновление описания не запускать wrong/win cue; после настоящего Apply остаётся текущий feedback.

## 7. Приёмка

1. **Классификация:** все одиннадцать cases из [CASES.json](CASES.json) дают указанные будущие outcomes. `exhausted` обрабатывается раньше `count=0`. Отдельно проверить внешний контроль `{count:1, exhausted:true}`: тоже budget outcome, без плана. Такой контроль не заявляется как реально наблюдённый текущий case.
2. **Сохранение доказательств:** оба ready-контроля отдают прежние rule/assignment/evidence; существующий verifier принимает их. Подменённый value/evidence, stale snapshot и повторное использование физического токена по-прежнему отклоняются существующим gate.
3. **Чистая подготовка:** нет изменений placements, trayOrder, boardRevision, history, coins, credits, lives, assisted и hintsUsed после выбора Explain, любого отказа, повторного выбора или Back. В UI не вызывается paid application для отсутствующего плана.
4. **Платное применение:** успешный ready → Apply проходит существующую проверку и одну транзакцию. Повтор operation ID и холодное восстановление сохраняют прежний receipt без второго списания. Достаточно существующих покрывающих тестов плюс проверка изменённого маршрута; переписывать эти системы не нужно.
5. **Endless:** разные причины на частичных и полностью заполненных полях до Submit дают одинаковую нейтральную проекцию и не переводят забег в assisted. Успешный Apply по-прежнему переводит. Ни подсветка уравнения, ни wrong cue, ни новый текст не выдают несовместимость до этого действия.
6. **UI:** на 320×480, 320×568 и 390×844, RU/EN, 100% тексты не обрезаны, горизонтального overflow нет, «К полю» и Apply доступны в исходном положении нижнего ряда без предварительного автоскролла теста. Смена Explain → Reveal → Explain не оставляет предыдущую причину. Длинное описание скроллится в `help-content`; меню не изменяет фоновые фишки.
7. **Показ результата:** приложить сравнимые before/after кадры и короткую GIF реального перехода «выбор Explain → сообщение → К полю», указав viewport, язык, mode и commit. Browser GIF доказывает browser-путь. Физический Android отдельно проверяет touch/Back и отсутствие лишнего haptic/audio; до этого PHONE_ACCEPTANCE остаётся UNKNOWN.

Сохранить обязательный проектный gate **`npm run check`** из AGENTS. Дополнительно выполнить целевые Help/session/UI проверки затронутого маршрута. Не добавлять новый solver, native Guru execution или весь difficulty/P6-проход как gate для этой узкой задачи. Полное качество difficulty и человеческая понятность не выводятся из этих fixture-тестов.

## 8. Воспроизведение baseline

Нужны Python 3 standard library и Node **24+**. Дополнительные npm-пакеты не требуются. Из директории этого пакета:

```sh
python3 verify_cases.py REPRODUCTION.json
```

Команда проверяет SHA пяти собственных исходных модулей, запускает их без изменения на одиннадцати cases и независимо перечисляет физические токены Python-оракулом. [REPRODUCTION.json](REPRODUCTION.json) сохраняет **PASS: 11 cases / 5 exact Git blobs**, включая единственное решение [5,4,1,2,2] при текущем `explain=null` и разницу budget=42 / normal.

`futureContractImplemented: false` обязателен: этот PASS подтверждает **пробел текущего baseline и качество воспроизводимого материала**, а не исправление. В собственных fixture IDs `901–903` используются только research inputs; они не регистрируют новые authored puzzles. Публикуемые файлы перечислены в [PUBLISH_FILES.json](PUBLISH_FILES.json); полные baseline документы и повторные копии UI для запуска не нужны.
