## Почему выбраны эти задачи

В текущем Help уже есть Direct/inverse/tray/intersection, проверка физического лотка и независимый verifier. Новый общий решатель для этих задач не нужен. Реальный пробел — одинаковый `null` для разных исходов поиска и общий текст, который не объясняет ограничение помощи.

В рекламной подсистеме уже есть request IDs, durable receipts, earned-only выдача, разделение награды и закрытия, сериализация команд баннеру. Реальный дефект — `bannerSent` обновляется до успешного завершения `setBanner`; rejection проглатывается, а то же желаемое состояние больше не отправляется.

Референсы используются непосредственно: методы и архитектура Guru помогают сформулировать явный результат операции; EasyFun показывает разделение fullscreen-операции и продолжения показа баннера. Конкретные типы исходов и восстановление после ошибки — наши адаптации, которые отмечены в ТЗ отдельно от поведения оригинала.

## Действующие продуктовые решения

- Помощь использует собственные алгоритмы на основании исследованного кода; планы проходят независимую проверку по видимому полю и физическим жетонам.
- Оплата, Apply и эффект завершения сохраняются атомарно. При отсутствии плана или отклонённом применении расхода нет. Reveal остаётся отдельным действием.
- В Endless новая диагностика до Apply не должна раскрывать дополнительные сведения о правильности размещений и не меняет правила assisted/Submit.
- ADS-01 дорабатывает существующий необязательный адаптер. Параметры частоты, rewarded receipts, набор placements, схема сохранения и выбор live SDK остаются действующими.
- UI использует текущие компоненты, Rubik, палитры и 100% текста. Приёмка затрагиваемых состояний: RU/EN, 320×480, 320×568, 390×844; размеры CSS и физические dp проверяются раздельно.

## Передача и приёмка

В каждом пакете есть исходные методы с build/SHA, отличие текущей игры, собственные воспроизводимые примеры, затрагиваемые файлы и сценарии приёмки. Воспроизведение дефекта на старом коде не является тестом исправления.

Разработчик перед работой сверяет новый HEAD активной ветки, затем реализует нужный пакет и фиксирует отдельные результаты unit/browser/APK/Android. Поле `ACCEPTED` и source parity обновляются только по соответствующим доказательствам. После реализации исследователь проверяет diff и обновляет [ADOPTION_LEDGER](../ADOPTION_LEDGER.json).
