# Crossmath: подсказки — контракт референса и критерии реализации

Ревизия 0.7 · 18 ноября 2026 · Guru 4.17.0 ARM64

Этот документ позволяет начать реализацию собственной системы помощи, сохраняя границу между подтверждённым поведением референса и предлагаемым контрактом нашего продукта. Он дополняет раздел 8 основного отчёта; не является утверждённым дизайном выпуска.

## Что установлено

1. Помощь имеет разные пути: раскрытие сохранённого ответа, прямой арифметический вывод и обучающее объяснение сложного хода.
2. Прямое раскрытие может вернуть несколько ошибочных фишек перед постановкой правильной. В стратегической ветке прямой помощи результат решателя выбирает клетку, а вставляемое число берётся из её сохранённого ответа.
3. Простой логический ход не открывает `StrategyTutorial`: возвращается пара «клетка → число». Сложный ход открывает соответствующий вид объяснения; для двух пересекающихся выражений предусмотрены два этапа.
4. Обучающее окно может вернуть **несколько назначений**, например цель и дополнительные клетки с единственным кандидатом. Это другой контракт, чем «одна расходная подсказка → одно правильное размещение».
5. Нативно проверенные арифметические помощники вернули правильные числа во всех 558 160 маскировках уравнений восстановленного банка. Повторяющиеся входы кешировались: 34 614 уникальных нативных вычислений включают и синтетические проверки.
6. Только прямыми выводами модель завершила 3 621 из 12 899 задач. Остальные 9 278 требуют других стратегий либо раскрытия; покрытие сложными объяснениями ещё не измерено.
7. Факторный примитив проверен на 18 819 синтетических случаях до границы установки: фильтр учитывает все делители и доступное количество фишек; 3 282 назначения и 15 537 отказов совпали с ожиданием. Это не измерение полного solve().

Основания: E36–E37, E43–E48 основного отчёта. Android и UI не запускались.

## Предлагаемый интерфейс нашей реализации

Ниже — проект технического контракта для разработки, **не восстановленные имена API Guru**.

| Объект | Поля и назначение |
|---|---|
| `BoardSnapshot` | Версия состояния; уравнения с индексами клеток; видимые значения; доступные экземпляры фишек; выбранная клетка; состояние текущего действия |
| `HintRequest` | Вид помощи `reveal` / `explain`; снимок; идентификатор операции |
| `HintPlan` | Цель; назначения `{cellIndex, value}`; возвращаемые ошибочные размещения; вид стратегии; опорные выражения; проверяемые шаги доказательства; версия снимка |
| `Explanation` | Семантический ключ шаблона, параметры, метки и ссылки на шаги; текст не участвует в арифметическом доказательстве |
| `HintOutcome` | `applied`, `no_step`, `stale_snapshot`, `busy`, `already_solved`, `insufficient_resource`, `invalid_proof`; фактические назначения и фактический расход |

Для `explain` решатель получает только видимую информацию и доступные фишки. Полное решение допускается у пути `reveal`; доступ к нему нельзя выдавать за логическое доказательство. Если игра выбирает один общий элемент управления, внутренний результат всё равно должен сохранять вид помощи.

Последовательность применения:

1. Создать неизменяемый снимок текущего поля и инвентаря.
2. Подготовить план, включая возврат ошибок и все назначения.
3. Проверить шаги независимым проверяющим кодом: арифметика, опоры, число экземпляров, отсутствие противоречий и объяснимость назначения.
4. Перед расходом сверить версию состояния и доступность действия.
5. Применить назначения и расход как одну сохраняемую операцию с устойчивым ID; повтор после перезапуска не начисляет и не списывает повторно.
6. Интерфейс показывает уже подтверждённый результат и освобождает блокировку при завершении или ошибке анимации.

Это рекомендуемая архитектура. В Guru порядок оплаты и запуска анимации иной; его статический разбор не доказывает атомарность сохранения.

## Арифметика и контент должны иметь один контракт

| Случай | Результат помощника Guru в стенде | Требование для нашей реализации |
|---|---|---|
| `? + 3 = 5` | 2 | Прямой вывод 2 и проверяемый обратный шаг |
| `6 ÷ 2 × 3 = ?` | 9 | Вычисление 9 |
| `2 + 3 × 4 = ?` | 20 | При обычном приоритете операций должно быть 14; либо такая грамматика явно запрещена валидатором контента |
| `3 ÷ 2 × 2 = ?` | Отказ | При разрешённых рациональных промежуточных значениях должно быть 3; при целочисленном ограничении выражение должно быть отвергнуто при подготовке контента |

Последние два примера искусственные: в банке не найдено неправильного прямого ответа. Для собственной игры недостаточно скопировать помощник и разрешить генератору любые сочетания операций.

Не переиспользуйте генераторный `allFactor` в решателе: для 12 он даёт `[1, 2, 6, 3]`, тогда как полный список делителей — `[1, 2, 3, 4, 6, 12]`. Проверка количества доступных экземпляров выполняется отдельно.

Используйте точные рациональные числа для проверок. Если продукт запрещает дробные промежуточные результаты, проверяющий код должен явно применять это правило; округление float не заменяет контракт.

## Критерии готовности модуля

| ID | Проверка | Условие приёмки |
|---|---|---|
| HC01 | Все позиции одиночного пропуска и все поддерживаемые операции | Проверка плана повторяет арифметику независимо; пропущенный ответ не передаётся решателю объяснений |
| HC02 | Два и более одинаковых числа | Используется количество экземпляров, а не только множество значений |
| HC03 | Пересечение двух уравнений | Общее значение совпадает; совместный расход фишек допустим; объяснение опирается на оба уравнения |
| HC04 | Уравнение имеет несколько арифметически правильных вариантов | Совпадение с сохранённым ответом не считается доказательством единственности |
| HC05 | Ход возвращает несколько назначений | Каждое назначение доказано; назначения применяются согласованно и не расходуют один экземпляр дважды |
| HC06 | Ошибочные числа занимают нужные фишки | Возвраты входят в план; правильные размещения сохраняются; набор фишек не меняется |
| HC07 | Поле изменилось после подготовки | План отклоняется как устаревший до списания |
| HC08 | Двойное нажатие и перезапуск во время сохранения | У операции один итог и один расход |
| HC09 | Решатель достиг лимита или не нашёл доказательство | Явный `no_step`; если выбран fallback, он помечен как раскрытие ответа |
| HC10 | Анимация или окно завершились с ошибкой | Поле и ресурсы согласованы; блокировка снята; повтор не дублирует применение |
| HC11 | Язык интерфейса меняется | Семантика доказательства не меняется; параметры соответствуют цветным меткам |
| HC12 | Полный собственный банк | Для каждой задачи есть протокол последовательности помощи; отдельно считаются логическое завершение и раскрытия |

HC01–HC12 — критерии будущей собственной реализации, **не выполненные тесты продукта**. Отдельные H01–H12 в листе проверки относятся к наблюдению референса Guru.

## Как измерять полноту

Не объединяйте четыре разных показателя: правильность одиночного вычисления; долю состояний с доказуемым ходом; долю полей, полностью пройденных объяснениями; возможность завершить поле раскрытиями. Для каждого храните отдельный результат и причину отказа. Наличие fallback не превращает неполное объяснение в проверенное.

Для Guru сейчас известны арифметическая проверка на восстановленных уравнениях, покрытие ограниченной моделью прямого вывода и доступность раскрытия в модели из ревизии 0.5. Факторный примитив отдельно проверен исходными инструкциями на синтетике; поле после этого назначения не обновлялось. Полный решатель, реальные объяснения, расход и сохранения в Android остаются следующей проверкой.
